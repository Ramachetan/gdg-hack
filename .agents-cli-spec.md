# Otto Roadside — Agent Spec

## Overview

A live, look-over-your-shoulder car-repair co-pilot, scoped to the **Ford F-150**. The user opens a web app, points their phone camera at the engine bay or dashboard, and talks naturally ("what's wrong?", "no, the part on the left"). The agent sees the camera and hears the mic continuously — not turn-by-turn — answers in a calm voice, lets itself be cut off mid-sentence, and acts on its own (diagnose, pull the right page from the F-150 owner's manual, locate help, book a shop) without being told which tool to use.

Architecturally: a forked copy of the ADK `bidi-demo` sample. FastAPI WebSocket backend. Gemini Live API native-audio model on Vertex AI. Browser frontend with continuous camera streaming at 1 fps and Web Audio worklets for 16 kHz mic / 24 kHz playback. A keyword-indexed retrieval tool over a bundled HTML F-150 owner's manual provides grounded visual references. Deployed to Cloud Run for a public URL.

## Example Use Cases

The demo must run this single end-to-end scenario cleanly:

1. User in a parking lot opens the public URL on their phone, taps "Look".
2. Camera streams ~1 fps to the agent; mic streams continuous PCM. User says "my car won't start."
3. Agent narrates in voice: "I can see your engine bay. Before we go further — hands off the battery terminals for now." (proactive safety).
4. Agent asks user to pan to a specific area: "Show me the area to the right of the air intake."
5. Agent diagnoses (e.g., loose battery terminal) and streams an **annotated frame** of the user's actual engine with the part circled, while narrating the fix.
6. User interrupts mid-narration: "wait, the cable on the left looks fine, I mean the other one." Agent stops speaking immediately, re-grounds on the new frame, continues.
7. User says "I can't do this myself." Agent calls `find_nearest_shop` → returns mock shop. User confirms. Agent calls `book_appointment` → returns mock confirmation. Voice says "Booked. Joe's Garage, 11:30 AM, 8 minutes away."

## Tools Required

All FunctionTools, automatically invoked by the live agent based on instruction. Mocked for the demo — real integrations are stretch goals.

| Tool | Purpose | Implementation |
|---|---|---|
| `annotate_frame(focus_part: str, instruction: str)` | Given the latest camera frame in session state + a focus description, returns a PNG with boxes/arrows drawn over the real frame. | Backend keeps the most recent JPEG blob in session state; tool uses PIL to draw annotations. Returns inline image part. |
| `consult_owners_manual(topic: str)` | Retrieves the relevant section from the bundled Ford F-150 owner's manual — returns section title, sanitized HTML snippet, and embedded images. | Pre-scraped F-150 manual stored in `app/static/manual/`. Keyword index (`manual_index.json`) maps topics/synonyms → section IDs. Tool returns `{section_id, title, html, images: [{src, caption}]}`. Frontend renders the snippet inline in the visual-guide panel. |
| `find_nearest_shop(symptom: str)` | Returns mock shop with name, distance, ETA, hours. | Hardcoded JSON for the demo. |
| `book_appointment(shop_id: str, time: str)` | Returns mock confirmation. | Hardcoded success response. |

## Constraints & Safety Rules

System instruction must enforce:

- **Grounding**: Every factual claim about *this* car must reference the camera frame ("I can see…") or a real reference. Never invent damage, parts, or events not visible. The owner's manual is the authoritative reference — when explaining a part or procedure, prefer `consult_owners_manual` over generating language from prior knowledge.
- **Visual honesty**: Annotations always overlay the user's actual frame. Reference imagery only comes from the bundled F-150 manual (real Ford diagrams/photos) — never generate or fabricate images depicting "what's wrong with the user's car."
- **Scope honesty**: Otto only knows the F-150. If the user shows a different car, it should say so and offer general safety guidance only.
- **Proactive safety**: If the camera shows the user near battery terminals, hot surfaces, moving belts, or fuel-system parts, warn *before* the user touches anything.
- **Honesty about limits**: If the frame is too dark, blurry, or doesn't show the part, agent says so and asks the user to reposition — never guesses.
- **Plain language**: Assume the user knows nothing about cars. No jargon without immediate explanation.

## Success Criteria

The hackathon brief's "definition of done" maps to four checks at demo time:

1. **Public URL works**: `https://otto-…-uc.a.run.app` opens on a judge's phone, camera + mic prompts appear, connection establishes.
2. **End-to-end loop runs live**: scenario above completes from "Look" through "Booked" in one continuous session on a real car or printed engine photo.
3. **Interruption visibly works**: judge can cut off the agent mid-sentence; spoken response stops within ~300 ms and agent responds to the new input.
4. **Grounded visual guide**: annotated frame is clearly the user's actual camera frame (not generated), shown inline while agent narrates the fix.
5. **Verifiable cloud platform**: `gcloud run services describe otto` shows the live revision; URL is the live Cloud Run endpoint.

## Architecture

```
Browser (HTML/JS + Web Audio worklets)
  │
  ├─ ws binary → server   PCM 16kHz mono mic chunks (continuous)
  ├─ ws text   → server   {type:"image", data:base64, mimeType:"image/jpeg"}  (1 fps, continuous when "Look" on)
  ├─ ws text   → server   {type:"text", text:"..."}                            (typing fallback)
  └─ ws text   ← server   ADK Event JSON (audio chunks, transcriptions, tool calls, interrupted, turn_complete)

FastAPI app (app/main.py — forked from bidi-demo)
  │
  ├─ upstream_task:   ws.receive() → LiveRequestQueue.send_realtime() or send_content()
  └─ downstream_task: async for event in runner.run_live(...) → ws.send_text(event.model_dump_json())

ADK Runner + Agent (app/otto_agent/agent.py)
  │
  ├─ Agent(model="gemini-live-2.5-flash-native-audio", tools=[annotate_frame, generate_diagram, find_nearest_shop, book_appointment])
  └─ RunConfig(streaming_mode=BIDI, response_modalities=["AUDIO"],
               input_audio_transcription, output_audio_transcription,
               session_resumption, proactivity=proactive_audio=True)

Gemini Live API (Vertex AI)
  └─ Native-audio bidi over WebSocket. Automatic VAD, interruption, and tool dispatch.
```

## Out of Scope

- Native mobile app, hardware integrations, smart-glasses input.
- Accounts, login, multi-user sessions.
- Fleet features, mechanic dashboards, payment.
- Real shop search (Google Places) and real booking integration — mocked.
- Polished onboarding flow.
- Production-grade error handling, rate limiting, observability.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Live API session caps at 10 min (Vertex). Demos may exceed. | Enable `session_resumption` in RunConfig (bidi-demo already does); reconnect transparently. |
| WebSocket cold-start on Cloud Run kills the first request. | Set `--min-instances=1` on deploy. |
| Mobile browser camera/mic permissions prompts can derail a demo. | Test on the actual demo phone the day before; keep a printed engine photo + laptop as the backup demo target. |
| Native-audio model may have stricter quota than half-cascade. | Have `gemini-live-2.5-flash` (half-cascade) as fallback model behind `DEMO_AGENT_MODEL` env var. |
| Continuous frame streaming may blow token budget. | 1 fps cap; pause frame send when user isn't speaking and no recent agent activity (stretch). |
